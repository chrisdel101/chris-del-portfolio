Aveva PI API to Esri Integrator Desktop App

Kvale Consulting | Project Dates: Jan 2026 - Oct 2026

TL;DR It builds background worker processes running on timed intervals, fetches data from a source API, and sends it to a target API.

This was a project started from scratch, and I wasn't given much. Just a few rough project parameters, a few suggestions about what would be nice to have, and told to get to work. So I came up with a plan to reseearch until I could out down some anchor points.

  1. Functional Requirements: Create a design document outlining requirements
  2. Architechture: Decide on monolithic vs client/server
  3. Tech Stack: Choose languages and frameworks
  4. Database: Crete ERD diagrams for database tables for then unknown database type - MsSQL is eventual chosen database
  5. Deployment and Production: Consider how the production enviroment will work

Functional Requirements

  • Primary task #1 - Fetch PI web API JSON data on timed intervals
    • Show the user all available JSON assets and make them fetchable.
    • Allow the user to select the data they want and save the choices as run settings.
    • Activate the run settings on timed intervals. Run the intervals as background tasks.
  • Primary task #2 - Shape the JSON payload and send to target
    • Allow user to choose from list of targets where to send the payload.
    • Clean, flatten, and process PI API data to match shape of chosen target. Send the payload.

Architechure

The decision was then to choose between two main designs:

  1. Monolithic: Bundle all processing and operations together in a single unit using C#
  2. Client/server: Create seperate back and front ends using web development technologies

We chose #2. Why? Plain HTML/CSS is the way to go for complex UI work.

Tech Stack

Finally the fun part! Deciding which languages and frameworks to use.

Choosing the client/server design meant we were truthfully just building a web app distguised as a desktop app - lets keep it all in Typescript.

  • Electron: C++ binary wrapper allowing us to run our frontend web code natively.
    • Runs a chromuim browser instance that steers the web development code into C++
  • Fastify: NodeJS Express-like framework used to build our backend REST API.
    • Known for speedm which we need be being very background-task heavy
    • Built-in APIs lile decorators and plugins keep things simple and effienct by default
  • VueJS: JS frameworks offer the best developer experience for building UI.
    • Advertised as the fastest of the virtual-dom frameworks, and works well with Electron.
  • Prisma: Modern ORM handles database interaction
    • If we needed to support different databases we didn't want to re-write our own SQL for each one.
    • Prisma supports all the major databases
  • Primevue: Vue UI component design suite

Deployment and Production

A requirement was that each instance be deployed individually to a clients's server as an executable. In this single tenancy model each instance of the app need be complely isolated behind a firewall or proxy, making it inaccessbile from the open internet. Without open-internet access we'd encounter fewer security threats, but it meant the entire processing and database apparatus needed to be created anew with each instance. The best packaging for user experience seemed to obviously be a desktop app.

DIY Dynamometer

Lytehorse | Project Dates: May 2022 - Aug 2022

TL;DR It builds background worker processes running on timed intervals, fetches data from a source API, and sends it to a target API.

I was given a few rough project parameters and a few words about what would be nice to have, and told to get to work building. I started thinkging about how.

Since I was the only developer on the project I had had near final-cut control:

  • How to structure the code
  • How to setup the GUI for user interaction
  • How to integrate safety features
  • And more....

The machine's construction was a solid metal frame inset with four 12 inch rollers that the vehicle sat on top of. These rollers were what ran the machine and what made this a dyno.

Each roller was connected to an electric motor for drive, brake, and torque/HP testing. The motors connected to Kelly motor controllers, which then connected to an Arduino. This was our way to commuicate.

On the user's end, a python program used our custom UART-based protocol to send and receive communications over serial. We used a Teensy microntroller since it has eight serial ports, and recieved asynchronous communication from both directions.

  • Primary task #1 was to develop native software using Python.
    • Using serial protocol, Python signalled Arduino. Arduino then signalled electric motor controllers on the machine.
    • Tools used included TKinter for GUI; multi-threading and TCP socket APIs for asynchronous communication.
  • Primary task #2 was to develop logic for Arduino microcontroller in C language. This handled communication between user and machine using serial.
    • Two-way serial communication meant Arduino accepted input from both Python and motor controller systems simultaneously.
    • Arduino signal directions: received serial input from Python, received serial input from motor controller, sent out appropriate serial output responses.
