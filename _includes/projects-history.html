Aveva PI API to Esri Integrator Desktop App

Kvale Consulting | Project Dates: Jan 2026 - Oct 2026

TL;DR It builds background worker processes running on timed intervals, fetches data from a source API, and sends it to a target API. This is the UI.

This was a project started from scratch, and I wasn't given much detail. Just a few rough project parameters, and a few suggestions about what would be nice to have. I set to researching and brainstorming until I could put down some project requirements before writing any code.

  1. Functional Requirements: Create a design document outlining requirements
  2. Architecture: Decide on monolithic vs client/server
  3. Tech Stack: Choose languages and frameworks
  4. Database: Create ERD diagrams for database tables for a then unknown database type - MsSQL was the eventual choice
  5. Deployment and Production: Consider how the production environment will affect the design

Functional Requirements

  • Primary task #1 - Fetch PI web API JSON data on timed intervals
    • Show the user all available JSON assets and make them fetchable.
    • Allow the user to select the data they want and save the choices as run settings.
    • Activate the run settings on timed intervals. Run the intervals as background tasks.
  • Primary task #2 - Shape the JSON payload and send to target
    • Allow user to choose from list of targets where to send the payload.
    • Clean, flatten, and process PI API data to match shape of chosen target. Send the payload.

Architecture

The decision was then to choose between two main designs:

  1. Monolithic: Bundle all processing and operations together in a single unit using C#
  2. Client/server: Create separate back and front ends using web development technologies

We chose #2. Why? Plain HTML/CSS is the way to go for complex UI work.

Tech Stack

Finally the fun part! Deciding which languages and frameworks to use.

Choosing the client/server design meant we were building a web app disguised as a desktop app - let's keep it all in TypeScript.

  • Electron: C++ binary wrapper allowing us to run our frontend web code natively
    • Runs a Chromium browser instance that steers the web development code into C++
  • Fastify: NodeJS Express-like framework used to build our backend REST API
    • Known for speed, which was important since the app is very background-task heavy
    • Built-in APIs like decorators and plugins keep things simple and efficient by default
  • Vue.js: JS frameworks offer the best developer experience for building UI
    • Advertised as the fastest of the virtual-dom frameworks, and works well with Electron
  • Prisma: Modern ORM handles database interaction
    • If we needed to support different databases we didn't want to rewrite our own SQL for each one
    • Prisma ORM supports all the major databases
  • PrimeVue: Vue UI component design suite

Deployment and Production

It is deployed to a client's personal server isolated behind a firewall or proxy, making it inaccessible from the open internet. All our design decisions needed to consider this.

Every deployment is a separate isolated instance. In this single tenancy model each installation needs to provide the entire processing and database apparatus for all app operations.

Shipping the frontend Electron side is pretty standard. The challenge was the Fastify backend. It needed to ship as an executable wrapped by some C# making it runnable as a Windows service. The client then brings their own MsSQL database.

DIY Dynamometer

Lytehorse | Project Dates: May 2022 - Aug 2022

TL;DR Dynamometers are used to test vehicles. They start at around $25,000. The goal here was to use off-the-shelf components to build one ourselves.

There were 3 main parts to this project.

  1. Prototyping and Hardware: Metal stuff, circuits, and making motors turn
  2. Arduino Programming: Programming embedded C++ in Arduino Studio
  3. Building Dyno Application: Main Python software to run the dyno

ProtoTyping and Electronics

We only achieved very basic controls for throttle and braking, but it was possible to control the vehicle and dyno separately.

The machine's construction was a solid metal frame inset with four 12-inch rollers used to move the mounted vehicle - essentially these are what made this a dyno. The vehicle sat on top and drove.

Each roller was connected to an electric motor for drive, brake, and torque/HP testing. The motors connected to Kelly motor controllers, which then connected to an Arduino. This was our way to communicate - everything used serial.

On the user's end, a Python program used our custom UART-based protocol to send and receive communications over serial. We used a Teensy microcontroller, which is a suped up Arduino. See image below. It had eight serial ports which we needed. We needed alot of serial ports to handles all asynchronous communication between devices.

I'm writing this years after this project ended and don't remember what everything here connected to anymore. There was much cool circuitry stuff happening, but this is all lost to the sands of time.

Harwdware Programmming

The gist: the computer sits on one end, the motor controllers on the other, and all comms pass through the Arduino. So Arduino had to handle bidirectional I/O from both sources:

  1. Source In/Out: Python desktop app <=> Arduino
  2. Target Out/In: Arduino <=> Motor controllers

1. Source In/Out

The app instigates the communication and Arduino listens by default using the void loop() API. Incoming messages are broken apart so we can identify what the instructions are. These are executed in part 2.

These needed to be fed into a simple state machine. To handle this we used something like JBD BMS Protocol, which is from an auto industry battery and electrics company. Our version uses the same start and end byte patterns, but the rest of ours is a mishmash.

Shown here is the scratch protocol. See how the book-ended by the JBD BMS hexadecimal byte patterns [0xDD] and [0x77]? This is the basis of the state processing. 

/* Message Format
*  Byte: 1       | Start bit [0xDD] (1 byte)
*        2:7     | Message Header (6-bytes)
*        8:X     | Message Data (variable byte Size)
*        X+1:X+2 | Message Checksum (message header + data size)
*        X+3     | End bit [0x77]
*/

Each stage is a different state trigger for a different action. 


            switch (rx_state)
            {

            case UART_RX_STATE_IDLE:
            {
              uint8_t data_in = UART_HOST_RX_SERIAL.read();
              // Check for the start bit pattern
              if (data_in == UART_RX_START_BIT_PATTERN)
              {
                // Move to the Header receive state
                set_rx_state(UART_RX_STATE_HEADER);
              }

              break;
            }
            case UART_RX_STATE_HEADER:
            {
              // Read the bytes into the header structure
              UART_HOST_RX_SERIAL.readBytes((char *)&rx_header, sizeof(msg_header_t));
              // Move to the Data receive state
              set_rx_state(UART_RX_STATE_DATA);

              break;
            }
            case UART_RX_STATE_DATA:
            {
              // If all of the expected data has been received
              if (rx_data_idx >= rx_header.len)
              {
                // Move to the Chksum receive state
                set_rx_state(UART_RX_STATE_CHKSUM);
              }
              else
              {
                // Add the received data to the buffer
                rx_data[rx_data_idx] = UART_HOST_RX_SERIAL.read();
                rx_data_idx++;
              }

              break;
            }
            case UART_RX_STATE_CHKSUM:
            {
              // Read the bytes into the checksum structure
              UART_HOST_RX_SERIAL.readBytes((char *)&rx_chksum, sizeof(msg_chksum_t));

              // Compute the checksum of the received header and data
              msg_chksum_t msg_chksum = 0;
              uint8_t i;
              uint8_t *rx_header_data = (uint8_t *)&rx_header;
              for (i = 0; i < sizeof(msg_header_t); i++)
              {
                msg_chksum = bsd_chksum(msg_chksum, rx_header_data[i]);
              }
              for (i = 0; i < rx_header.len; i++)
              {
                msg_chksum = bsd_chksum(msg_chksum, rx_data[i]);
              }

              // Compare the calculated and received checksums
              if (msg_chksum == rx_chksum)
              {
                // If match, move to the End bit receive state
                set_rx_state(UART_RX_STATE_ENDL);
              }
              else
              {
                // Otherwise, reset to the Idle state
                set_rx_state(UART_RX_STATE_IDLE);
              }

              break;
            }
            case UART_RX_STATE_ENDL:
            {
              uint8_t data_in = UART_HOST_RX_SERIAL.read();
              // Check for the end bit pattern
              if (data_in == UART_RX_END_BIT_PATTERN)
              {
                // Message is valid, pass to process function
                uart_rx_message(rx_header.msg_id, rx_header.bus_id, rx_header.len, rx_data);
              }

              // Move back to Idle state to receive next message
              set_rx_state(UART_RX_STATE_IDLE);

              break;
            }
            default:
            {
              // In an invalid receive state, move back to Idle
              set_rx_state(UART_RX_STATE_IDLE);

              break;
            }
            }
